## 2. 웹앱 기반 변경

### 2.1 이름
- 화면 머리글, `index.html` `<title>`·description, `app/README.md`, 루트 `README.md`의 「아산 밥때」를 「밥타임」으로. 내부 저장 키 접두사 `babttae.`는 유지(기존 사용자 설정 보존).

### 2.2 식당 모델
- `DiningHallId = 'east' | 'west' | 'new'`, `VenueId = 'east' | 'west' | 'new' | 'boxLunch'`.
- 메뉴 묶음: `MenuGroupId = 'east' | 'westNew'`. 메뉴 데이터는 기존처럼 `westNew` 묶음 하나로 저장하고, 서관·신관 식당은 둘 다 이 묶음을 참조한다(`VENUES[x].menuGroup`).
- 운영시간 창: 서관·신관 각각 평일 중식 11:00–14:00(기존 westNew 창을 둘로).
- `VENUES` (이름 / 짧은 이름 / 글자 타일 / 위치):
  - east: 동관 직원식당 / 동관 / 동 / 동관 B1F (official)
  - west: 서관 직원식당 / 서관 / 서 / 서관 B1F (estimated)
  - new: 신관 직원식당 / 신관 / 신 / 신관 B1F (estimated)
  - boxLunch: 간편식 도시락 / 도시락 / 도 / 동관 B1F 직원식당 앞 (estimated)
- 대기열 모델 상수(시작값, 아래 보정 목표를 만족하도록 구현 계획에서 확정):
  - west·lunch: peak 12:05, σ 25분, 기본 도착 9/분, 처리 7/분
  - new·lunch: peak 12:00, σ 25분, 기본 도착 6/분, 처리 7/분
  - east는 기존 값 유지
- 보정 목표(수요일 2026-10-14 12:20): 동관 `queue|busy`, 서관 `queue`(5–10분), 신관 `ok`. 홈 결론: "지금은 신관이 바로 드실 수 있어요".
- 직원 입력·품절·알림 구독은 식당 3곳 단위. 기존 저장값의 `westNew` 항목은 무시(오류 없이).
- 테이크아웃: 원본 메뉴표대로 "동관" / "서관·신관" 두 매장 표기 유지.

### 2.3 화면 반영
- 홈: 식당 줄 3개(동관·서관·신관) + 도시락. 결론 타일은 선택된 식당 하나의 글자.
- 메뉴: 중식 비교는 2열(동관 / 서관·신관 공통) 유지, 열 제목에 "서관·신관 공통".
- 검수 직원 화면·알림 화면: 식당 선택·스위치 3개.
- 지도: 건물 5개(동관, 서관, 신관, 교육연구관, 아산생명과학연구원)를 단순화한 배치도로, 식당 핀 4개(동관·서관·신관·도시락). 캡션 "단순화한 배치도" 유지. 배치는 추정이며 데이터 파일에서 수정 가능.

## 3. 새 기능

### 3.1 이동+대기 총 소요시간 추천
- 데이터 `app/src/data/buildings.ts`: 건물 5개 `BuildingId = 'east' | 'west' | 'new' | 'eduResearch' | 'asanLife'`(이름: 동관, 서관, 신관, 교육연구관, 아산생명과학연구원)와 도보 시간(분, 추정):

| 출발 \ 식당 | 동관 | 서관 | 신관 |
|---|---|---|---|
| 동관 | 2 | 7 | 8 |
| 서관 | 7 | 2 | 4 |
| 신관 | 8 | 4 | 2 |
| 교육연구관 | 6 | 8 | 9 |
| 아산생명과학연구원 | 7 | 9 | 10 |

- 설정: 홈 시트 상단 칩 "근무 건물: {이름|미설정}" → 시트에서 5개 중 선택(지우기 가능). `prefs`에 저장.
- 계산: 식당별 총 소요 = 도보 + (도착 시각 기준 예상 대기). 도착 시각 = now + 도보.
- 건물 설정 시 홈 결론: 총 소요 최소 식당. 문구 "지금 출발하면 {식당}이 가장 빨라요", 보조 "걸어서 {n}분, 도착하면 {바로 드실 수 있어요 | 약 {m}분 기다려요}". 식당 줄에 "걸어서 n분" 추가. 미설정 시 기존 규칙.
- 도보 시간 옆에 "추정" 표기.

### 3.2 운영자(영양팀) 대시보드 `/ops`
- 진입: 시연 시간 시트의 "운영자 화면 열기" 링크(검수 직원 링크 옆). 탭에는 없음.
- 구성(모두 "모의 데이터" 표기):
  1. 지금 상황: 식당 3곳 상태·예상 대기·직원 입력 여부.
  2. 오늘 시간대별 입장 추정: 식당별 10분 단위 막대(모델의 도착 인원 합).
  3. 품절 기록: 오늘 품절 입력(식당·끼니·코스·시각).
  4. 만족도·잔반: 별점 평균과 남김 정도 비율(시드 고정 모의값 + 이 브라우저의 평가).
  5. 내일 준비 제안: 같은 요일 예측으로 식당별 피크 시각, 예상 이용 인원; 예상 대기 ≥ 10분 구간이 있으면 "{HH:MM}~{HH:MM} {식당} 배식 라인 추가 검토"; 내일 주메뉴 인기도가 1.2 이상이면 "{식당} {메뉴} 준비량 상향 검토".
- 데스크톱 2단 레이아웃, 모바일 1단.

### 3.3 식당 상세 시트와 평소 혼잡 패턴
- 홈 식당 줄을 누르면 상세 `Sheet`(제목 = 식당 이름): 오늘 예측 막대(크게), 평소 혼잡 패턴 표(요일 × 10분 칸; 서관·신관은 월–금 11:00–14:00, 동관 중식은 운영 요일 전체), 도보 시간(설정 시), 위치(지도로 이동 링크), 오늘 메뉴 요약.
- 패턴은 저장 주간의 각 요일 메뉴 인기도로 모델을 돌린 결과. 칸은 색 + 단계 약자(여/보/줄/혼)와 접근성용 표(sr-only)로 표현. 차트 작성 전 `dataviz` 스킬을 따른다.

### 3.4 원산지
- 메뉴 화면 식당 탭 중식 아래 한 줄: "원산지(10월 3주차 안내 기준): 소고기 호주산, 돼지고기 국내산·외국산, 닭고기 국내산, 쌀 국내산, 김치(배추·고춧가루) 국내산". 데이터는 `menus`에 주간 공통 값으로.

### 3.5 테스트
- 단위: 3곳 보정 목표, `westNew` 저장값 무시, 총 소요 계산과 추천 선택(건물별), 패턴 계산(결정성·요일별 차이), 내일 준비 제안 규칙, 원산지 표시.
- E2E: 근무 건물 설정 후 홈 결론 변화, 식당 상세 시트 열림, `/ops` 열림과 콘솔 오류 0, 다크 모드에서 가로 넘침 없음. 기존 테스트는 3곳 구조에 맞게 갱신.
- 스크린샷 점검: 5개 화면 + `/ops` × 390/1280 × 라이트/다크.

## 4. 제안서 변경
- 이름: 표지·머리글("밥타임 상세 제안서")·본문 전체 「밥타임」.
- 식당 3곳: 표 2를 동관 / 서관 / 신관 3열로(서관·신관 같은 메뉴·시간 주석), 그림 1·2, 5장 집계 단위를 식당 3곳으로. 건물 언급은 5개 기준.
- 4장 표 5에 3줄 추가: 이동+대기 총 소요시간 추천 / 운영자 대시보드(영양팀·식당 운영 주체의 배식 인력·준비량 조정) / 평소 혼잡 패턴·원산지 안내. 그림 2에 "걸어서 n분" 반영.
- 7장 추가:
  - 7.x 시범 운영 설계: 대상 식당 3곳, 기간 가정(기준값 측정 2주 → 시범 4주 → 비교), 같은 요일·시간대 도입 전후 비교, 설문 표본 목표(가정).
  - 성과 지표 표: 피크 평균 대기, 대기 10분 이상 비율, 정보 확인 시간, 이용자 만족도, 잔반량, 알림 구독률 — 지표별 측정 방법·기준값 측정 시점·목표값(가정).
  - 단계별 필요 자원 표: 인력(역할)·데이터·시스템 작업·협의 사항. 금액은 쓰지 않는다.
- 8장: 표 11 측정 지표를 성과 지표 표와 일치.
- 부록 A. 설문 문항(도입 전후 공통 8–10문항: 식사 소요시간, 대기 빈도, 정보 확인 시간, 만족도 5점, 결식 빈도 등).
- 분량: 본문(표지~참고문헌) 15쪽 이내, 부록 포함 16쪽 이내. `verify.mjs`의 쪽수 기준을 12–16으로, `## 부록` 존재 확인 추가. 금지어 규칙 유지.
